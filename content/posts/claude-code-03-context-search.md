[上一篇]({{< relref "claude-code-02-query-loop.md" >}})里，消息历史每一轮都变长，塞不下时才压缩。这篇把压缩和找代码放在一起。两者解决的是同一件尴尬：窗口有限，过程却很吵。材料来自 [图解 Claude Code](https://xiaolinnote.com/claudecode/) 的压缩篇和检索篇。

## 一、五层，能不压就不压

压缩不是等到爆了再摘要一次。专栏把实现整理成从轻到重的五层。原则是：能不压就不压；必须压时从最轻的手段开始。前面几层把大块垃圾处理掉，后面几层就不必上场。

| 层 | 做什么 | 代价 |
|----|--------|------|
| 大结果落盘 | 单条工具结果过大（专栏给出的量级是约 50KB）时，全文写到磁盘，消息里留一份短预览。同一条消息里的工具结果还有总量上限。 | 本地，不调模型。需要时再 Read。 |
| Snip | 模型在正常回答那一轮里，用工具按消息 id 标出可以丢掉的早期消息。本地删除，并留下「前面已被清理」的边界。释放出的空间会告诉后面的压缩，避免两层做同一件事。 | 搭在本轮上，不另开一次摘要。 |
| Micro-Compact | 距离上一次 API 调用大约超过一小时，服务端的提示缓存多半已经失效。这时清掉可以再取的工具结果（Read、Bash、Grep、Glob、检索、编辑、写入），只留最近几条。子 Agent 的结论和任务状态留下。 | 本地。 |
| Context Collapse | 占用到大约九成时做读时投影：原始历史不动，发给模型的是一份更短的视图。大约九成五再加重。 | 专栏说明这是内部实验，对外版本里常常被裁掉。 |
| Auto-Compact | 接近窗口上限时，把整段对话交给摘要器重写。 | 一次额外的模型调用。 |

第四层和第五层不同时开。它们的触发线挨得很近，一起跑会互相把对方准备保留的内容清掉。对外能稳定看到的兜底是 Auto-Compact。

## 二、Auto-Compact：固定缓冲，全量重写

触发不按轮数，也不按「用了百分之八十」。它用离窗口上限的固定距离。

有效窗口先扣掉一块给摘要自己的输出。专栏引用的实现里，这块是 2 万 token：他们统计过摘要输出，极端分位大约 1.7 万，再向上取整。然后再扣 1.3 万，作为提前触发的第二道缓冲。离原始窗口大约 3.3 万 token 时就开始压。窗口以后变到 50 万或 100 万，这条绝对距离不用跟着百分比膨胀。摘要该占的地方不会因为窗口变大就该占得更多。

自动和手动 `/compact` 走同一个压缩函数。手动可以附一句「这次请保住某个 bug 的上下文」。自动不接受这句，并且禁止摘要里再追问，免得正干活时被一个新问题打断。

自动模式还有熔断：连续失败三次就停止再试。专栏提到，曾经有大量会话在压缩失败后反复重试，账单被打穿。摘要任务自己如果再触发压缩，会递归。来源标成 `compact` 或会话记忆的查询直接不再压缩。

压缩的取舍和多数框架相反。常见做法是留下最近若干轮，把更早的历史收成一段。Claude Code 把整段历史送进摘要器，重写一份。理由是：中间的轮次模型本来就看得模糊，留着是一份半清楚的原文。目标、做到哪一步、犯过的错、下一步，用结构化摘要更可核对。

不能只靠摘要保住的东西，走别的通道重新放回来：`CLAUDE.md` 这类记忆文件下一轮照常加载；最近读过的文件可以作为附件再注入；正在跑的后台子任务状态要留下来，否则主 Agent 会忘记自己派出过谁。对话细节可以归档，员工手册和手头那几份文件要回到桌面上。

## 三、找代码：像人一样现查

程序员接手陌生仓库，先看目录，再按关键字搜，再打开命中的那几行。没有先把整个仓库嵌成向量。Claude Code 把同样的三步交给模型：

- **Glob**：按文件名模式找，例如 `**/*.tsx`。结果按修改时间倒序，最近改过的排前面，并设一个文件数上限，超出就截断，让模型收紧模式再搜。
- **Grep**：按内容搜，底层是 ripgrep。尊重 `.gitignore`，不去扫依赖目录。输出可以是匹配行、仅文件路径或仅计数。搜索走这个工具，而不是在 Bash 里自己敲 `grep` 或 `rg`，这样权限和输出格式有单独的闸门。
- **Read**：默认只读开头的一段（专栏写的是大约 2000 行）。已经知道位置就用偏移和长度。每次直接读磁盘上的当前内容，不经过一份会过期的索引。

一次「登录写在哪」会变成：Glob 出候选文件，Grep 在里面定位行，Read 只读那一段。每一步看见上一步的结果再决定下一步。这是多轮探查。RAG 常见的形态是一次召回 Top-K，然后一次性作答。召回偏了，模型只能在那一叠片段里作答。这里召回偏了，下一轮可以换关键字。

Grep 单独做成工具，还有三个原因。Bash 什么都能跑，搜索这种高频动作需要自己的权限闸。纯文本输出浪费 token，三种粒度让模型按需要。ripgrep 比在 Bash 里套传统 grep 更适合大仓库。

## 四、超过三次查询，就派一个人去查

「把认证流程摸清」可能要十几次搜索和阅读。这些中间结果若都留在主对话里，等它回头写代码时，真正的任务已经被检索日志挤到边上。

主 Agent 通过 Agent 工具派一个 Explore 子 Agent。子 Agent 有自己的上下文，工具收成只读：Grep、Glob、Read，以及只读的命令。它不能改文件，也不能再派下一层，避免检索递归。它在自己的窗口里搜很多轮，交回一段结论。主对话只多出这段结论。

专栏引用的工具说明把分界写得很具体：目标明确、几次就能定位的，直接用三件套；明显要超过大约三次查询的开放式探索，才用 Explore。三块互不依赖的模块可以同时派三个，一起回来汇报。

## 五、什么时候仍然该用 RAG

六条理由说明编程 Agent 的默认检索为什么是现查：

1. 打开就能搜，不必先建索引。
2. 读的是磁盘上刚改过的文件。
3. `getUserById` 就是这个符号，不是一堆相似函数。
4. 只读真正要看的行，不必先给整个仓库做嵌入。
5. 每一步搜索用户看得见，召回错了可以改关键字。
6. 搜什么由模型按上一步结果决定。

这些理由成立的地方，是「仓库在本地、符号要精确、文件刚刚被改过」。文档问答、跨资料的语义回忆、代码并不在磁盘上的知识库，仍然适合先检索再回答。本站 [系列二]({{< relref "agent-build-00-roadmap.md" >}}) 的企业知识助手就是后一种：答案在文档里，不在某个函数名上。两种做法对应两类材料，不必互相替代。

## 六、小结

- 压缩从落盘、裁旧消息、清可再取的工具结果做起，全量摘要是最后一层，按离上限的固定距离触发。
- 摘要重写整段历史。手册、最近读过的文件、后台任务用别的通道放回来。压缩失败三次就停，摘要任务自身不再触发压缩。
- 找代码用 Glob、Grep、Read 读当前磁盘。开放式探索派只读的 Explore，主对话只收结论。
- 符号级、会变的本地代码适合现查。语义型文档适合 RAG。
