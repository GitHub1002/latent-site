[上一篇]({{< relref "claude-code-01-toolkit.md" >}})把会话外面的六件套放好了。这篇看会话里面那颗心脏。材料来自 [图解 Claude Code](https://xiaolinnote.com/claudecode/) 对主循环的拆解，下面用本站自己的话重写。

你在终端输入「修这个 bug」并回车。第一次模型回复常常不是补丁，而是「我要先读那个文件」。运行时去读，把内容塞回去。它可能又要跑测试。来回多轮，它才给出修改。这个循环在实现里叫 `queryLoop`。

能跑通 demo 的骨架很短：调模型，有工具就执行，没有就停。生产里大部分代码在处理另一类事：中途取消、工具没跑完、输出被截断、上下文被拒收、轮数跑飞。正常路径短，异常路径长。

## 一、它不把思考写成一段文本

ReAct 把每一轮拆成 Thought、Action、Observation。模型先写「我打算读 config」，再选工具，再看结果。2022 年前后，显式思考能托住推理还不稳的模型。放到编程 Agent 上有三笔成本：每轮思考都占上下文；应用层要从文本里把动作抠出来，格式一飘就断；强模型已经能在内部把推理做完，再写一遍是重复。

Claude Code 用的是工具调用循环。模型内部可以做一段不进入对话的思考（Extended Thinking），对外只交两种结果：

- `tool_use`：我要用这个工具，参数是这些。运行时执行，把 `tool_result` 接回去，循环继续。
- 没有工具调用，结束原因为 `completed`：这轮话说完了。

应用层不解析「Final Answer」这类句子。有没有工具块，就是继续还是停。下一步做什么，留给模型。

这和 [Harness 的 agent-loop]({{< relref "harness-01-plugin-engine.md" >}}) 是同一类心脏：循环本身不管读文件的细节，只会把工具请求交出去。差别是 Harness 把循环做成可替换插件；Claude Code 把循环留在引擎里，把能力做成工具。

## 二、一句话穿过四层

从外到内是 `ask`、`QueryEngine.submitMessage`、`query`、`queryLoop`。每一层都是异步生成器，用 `yield*` 把内层抛出的事件原样送到外层。所以最里面每吐一个字，调用方都能马上看到。

| 层 | 职责 |
|----|------|
| `ask` | SDK 的一次性入口。新建一个 `QueryEngine`，把这句话交进去。 |
| `QueryEngine` | 会话记账：消息历史、文件缓存、被拒绝过的权限。斜杠命令、系统提示、上下文注入发生在这里。 |
| `query` | 流式包装。循环只管转，收尾和清理不塞进循环本体。 |
| `queryLoop` | `while (true)`。准备、调用、判断、执行、写回。 |

`query` 看起来只是包了一层。它把「转完还要通知谁」从心脏里拿出去，心脏只对一轮一轮的状态负责。

异步生成器不是等一整桶水再端走。模型每吐一段、工具每完成一件，事件就流出来。你看到的逐字输出，以及下一节的「模型还在说话、工具已经开跑」，都依赖这条水管是通的。

## 三、一轮里的五步

`queryLoop` 把跨轮要记住的东西放在一个 `State` 里：消息列表、轮数、输出截断已经补救几次、这一轮是否已经压缩过。每轮开头读它，结尾构造一个新的写回去。计数和防重复标志摊在明处，不藏在闭包变量里。藏起来的计数器是死循环的常见来源。

每一轮按这个顺序：

1. **准备消息。** 先按原样发送。API 以上下文过长拒收（`prompt_too_long`）时，才压缩一次再重试。压缩要另调一次模型做摘要，能不压就不压。`hasAttemptedReactiveCompact` 保证同一轮只压一次，避免「压完仍塞不下、再压」的圈。压缩的分层在 [03]({{< relref "claude-code-03-context-search.md" >}})。
2. **流式接收。** 文字块立刻向外抛。`tool_use` 块先攒起来。
3. **判断。** 变量 `needsFollowUp` 只看一件事：这轮回复里有没有 `tool_use`。没有，返回 `completed`。
4. **执行工具。** 能并行的并行，会改状态的串行。见下一节。
5. **写回。** 助手消息和每条 `tool_result` 追加进历史，轮数加一，回到循环头。

跑了二十轮，第二十轮看到的是前十九轮的对话和工具结果。历史像滚雪球，所以才需要压缩。

停下来不只有 `completed`。专栏整理出的代表性原因包括：

| 原因 | 发生了什么 |
|------|------------|
| `completed` | 模型没有再要工具 |
| `max_turns` | 调用方设了上限，到顶止损 |
| `aborted_streaming` | 模型还在吐字时被取消 |
| `aborted_tools` | 工具执行中被取消 |
| `prompt_too_long` | 压过一次仍然进不去窗口 |
| 输出超长无法恢复 | 续写多次后仍被截断 |
| `stop_hook_prevented` | 用户的 Stop Hook 拦住结束 |
| `image_error` | 图片格式不被接受 |

实现里的原因码更多。记这些就够看出设计：每一种退出都对应一次真实故障，而不是一个笼统的「出错了」。

## 四、模型还在吐字，工具已经开跑

朴素做法是等模型流完，收齐所有 `tool_use`，再一个个执行。吐字的时间和执行的时间完全串开。

`StreamingToolExecutor` 在流里认出一个完整的工具块，就立刻 `addTool` 丢到后台。模型继续往下说。流结束后 `getRemainingResults` 把已经跑起来的结果收回来。你点到「红烧肉」的那一刻后厨就开始做，不必等整桌菜名说完。

并行有边界。工具在定义时声明自己是只读还是会改东西。Read、Grep、Glob 可以一起跑。Edit、Write、会改状态的 Bash 必须串行，否则两次写会互相覆盖。声明漏了，框架按会改东西处理，强制串行。宁可慢，也不靠默认值去赌并发安全。

[PocketPilot]({{< relref "pocketpilot-03-policy.md" >}}) 把「会改东西」停下来等人批。Claude Code 把「会改东西」标成不可并行，再交给权限系统和 Hook 决定能不能执行。两套都要求工具出厂时带上这个属性，而不是事后用正则猜。

## 五、失败了也要能接上下一轮

Anthropic 的消息协议要求：每个 `tool_use` 都要有配对的 `tool_result`。缺一个，下一轮请求会被拒收。

工具没开始跑、跑到一半被取消、或者中途换了模型，历史里就会留下孤立的 `tool_use`。主循环补一条用户侧的 `tool_result`，标上 `is_error`，写明没执行的原因，并带上原来的工具调用 id。模型下一轮看得到「这个工具失败了」，API 也认这是一对。取消之后你还能继续说话，靠的是这条补上的错误结果，而不是把半截历史扔掉。

输出被截断时分两段处理。第一次可以静默把输出上限调高再试这一轮，界面上只是慢了一点。仍然截断，就在下一轮消息里要求模型从断点接着写，不要道歉，不要复述刚才在干什么，把剩下的工作拆小。这种续写有次数上限，专栏里写的是三次。超过就带着明确原因退出，不无限 nudge。

Plan Mode 没有另写一个循环。模型调用 `EnterPlanMode` 之后，权限收成只读，只能 Read、Grep、Glob，计划写到 `.claude/plans/`。探索期间系统会隔若干轮提醒它还在计划里。`ExitPlanMode` 要人确认，确认后写权限回来，仍是同一个 `while (true)`。模式是两个工具，引擎不用为「计划」开特例。简单的错别字不必进这个模式。

## 六、小结

- 有 `tool_use` 就继续，没有就结束。思考留在模型内部。
- 四层都是生成器，事件边产生边往外送。跨轮状态放在一个对象里。
- 只读工具在模型还在吐字时就开跑。会改状态的工具串行，漏声明就当成会改。
- 孤立的工具调用要补一条错误结果。压缩和续写都有一次或三次的上限。
